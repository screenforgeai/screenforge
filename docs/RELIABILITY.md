# Recording & Export Reliability

What issue #20 checked, what was fixed, and the tests that still need real hardware. Some of this work was done in a Linux container with no display, monitors, audio devices, macOS or Windows. Those parts were checked by reading the code and by unit tests, not on real setups. The manual matrix at the end covers the rest.

## Multiple monitors

### Found but not changed (needs a build or hardware to verify)

- **Windows helper is not DPI-aware.** `native/windows/ScreenforgeCapture` never calls `SetProcessDpiAwarenessContext`. Its low-level mouse hook reports physical pixels anyway. But `GetCursorInfo` (the extra "move" event sent when the cursor shape changes) and `GetWindowRect` (window bounds for window recording) return coordinates scaled for the system DPI. On mixed-DPI setups those can disagree with the hook's coordinates. Suggested fix: call `SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)` at the top of `main.cpp`, then check window recording and cursor-shape changes on a mixed-DPI setup.
- **Linux X11 with a scale factor other than 1** (`GDK_SCALE`, `Xft.dpi`). Electron reports display bounds in DIP, but x11grab and uiohook use pixels. With scale 1 (the usual X11 setup) they are the same. With HiDPI, the grab region and cursor positions are probably off by the scale. Needs checking on such a machine; `display.nativeOrigin` and `scaleFactor` would give the pixel rectangle.
- **Resolution or scale change mid-recording** is only logged. Capture continues at the old size, and cursor positions use the bounds from the start.
- The dead `gdigrab` branch in `buildCaptureArgs` (Windows always uses the native helper) passes DIP bounds to gdigrab. It is not used today.

## System audio

| Platform             | Capture path                                                           | System audio                                                                  |
| -------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| macOS 13+            | native ScreenCaptureKit helper (`capturesAudio`, own process excluded) | Recorded                                                                      |
| macOS 12 and earlier | FFmpeg AVFoundation fallback (`Capture screen N:none`)                 | Not recorded                                                                  |
| Windows              | native helper, WASAPI loopback of the default output device            | Recorded (the helper logs and skips it if the device's mix format is unusual) |
| Linux X11            | FFmpeg x11grab                                                         | Not recorded                                                                  |
| Linux Wayland        | PipeWire portal stream via `getDisplayMedia({ audio: false })`         | Not recorded                                                                  |

`getSystemAudioSupport()` (`electron/modules/recording/system-audio.ts`, tested) returns `supported` or a reason (`macos-too-old`, `linux-not-supported`, `platform-not-supported`). Where it isn't recorded, the microphone tooltip and the microphone menu say so in all seven languages. Before, it was just missing from the recording.

Not done: recording Linux system audio from the PulseAudio/PipeWire monitor source (e.g. FFmpeg `-f pulse -i <sink>.monitor` next to x11grab, or `audio: true` on the portal request). That is a feature, and it needs a decision on mixing it with the microphone track.

## Preview vs export

The preview and the export both decode the recording with Chromium, then the export re-encodes the composited frames with WebCodecs and FFmpeg adds the audio. Checked:

| Check                                 | Result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | How                                                                                                                                                                                                                       |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **X11 recordings' colour**            | **Bug, fixed.** The capture converted RGB to YUV with FFmpeg's default BT.601 matrix and didn't tag the file. Chromium reads untagged H.264 as BT.709. The brand orange `212,69,35` came back as `225,82,36`, red as `255,24,0`, blue as `0,14,253`, in both the preview and the export. The capture now converts with `scale=out_color_matrix=bt709:out_range=tv` and tags `-colorspace bt709 -color_primaries bt709 -color_trc bt709 -color_range tv`, which comes back as `212,69,37`. | Encoded colour bars with the capture's conversion and decoded them with headless Chromium's `VideoDecoder`. `capture-args.colour.test.ts` repeats the round trip with FFmpeg.                                             |
| **Export encoder colour**             | Consistent. WebCodecs H.264 (OpenH264, software) outputs full-range BT.709 with the sRGB transfer, and the stream says so (VUI and the `decoderConfig.colorSpace` that mediabunny writes into the MP4 `colr` box). The bars decode back within ±1 of the source.                                                                                                                                                                                                                          | Headless Chromium 153 `VideoEncoder` with the app's config, checked with `ffprobe` and decoded with FFmpeg. Electron 45 ships an older Chromium, and hardware encoders (VideoToolbox, Media Foundation) were not checked. |
| **Audio mux keeps colour and timing** | The final FFmpeg step (`-c:v copy`) keeps the colour tags and `colr` box and a constant frame rate.                                                                                                                                                                                                                                                                                                                                                                                       | Ran the same mux args on the WebCodecs output; `ffprobe` showed matching tags and evenly spaced 1/30 s timestamps.                                                                                                        |
| **Frame pacing**                      | Constant. Every exported frame's timestamp is `round(frameIndex / fps × 1e6)` µs, and mediabunny's track uses the export fps as its timescale. No `-vsync`/`-fps_mode` is needed because FFmpeg only copies the video.                                                                                                                                                                                                                                                                    | Code reading (`captureTimeline.ts`, `videoMuxer.ts`, `ffmpeg/jobs/export.ts`).                                                                                                                                            |

Open question: exports are **full-range** with the **sRGB transfer** (what Chromium's encoder chooses for RGB input). Browsers, QuickTime and FFmpeg-based players honour that. Players that ignore the full-range flag show slightly washed-out blacks and whites. Switching to limited-range BT.709 would need a conversion pass after the encoder (WebCodecs has no output colour-space option), which costs export time.
